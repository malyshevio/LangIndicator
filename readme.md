# Индикатор раскладки у курсора ввода (Linux, Wayland, GNOME Shell)

Утилита показывает всплывающий индикатор текущей раскладки клавиатуры («RU», «EN» и т.п.) **непосредственно возле курсора ввода (текстовой каретки)** в активном приложении. Индикатор появляется при переключении раскладки и при запуске утилиты.

Обычное Wayland-приложение (Rust или Go) не может получить позицию каретки другого приложения из-за изоляции композитора, поэтому решение реализуется как **расширение GNOME Shell**.

---

## 1. Ключевые требования и ограничения

- **Целевая среда:** Linux + Wayland, GNOME Shell.
- **Позиционирование (критично):** Индикатор появляется **строго у курсора ввода (каретки)**, а не у курсора мыши. Позиция мыши не является приемлемым fallback-ом. Если точное позиционирование у каретки технически невозможно, это должно быть явно задокументировано как ограничение, а не заменено позицией мыши.
- **Триггеры:** 1) Переключение раскладки; 2) Запуск утилиты (кратковременный показ текущей раскладки).
- **Языки/технологии:** Основная логика отображения интегрирована в композитор (GNOME Shell Extension — JavaScript, GJS). Rust или Go могут использоваться для вспомогательных задач (например, мониторинг XKB-состояния, D-Bus-сервис), но **не как основной GUI-слой**, поскольку они не имеют доступа к позиции каретки других приложений.
- **Терминал:** Не требуется.

---

## 2. Технические исследования и обоснование архитектуры

1. **Почему обычное Wayland-приложение не может получить позицию каретки?**
   - Протокол `zwp_text_input_v3` позволяет клиенту (приложению) отправлять композитору `set_cursor_rectangle` (позицию каретки в координатах поверхности). Однако эта информация доступна только композитору (и, возможно, input-method), но не другим клиентам. Обсуждение в fcitx5 подтверждает: при попытке получить `SetSpotRect` из Wayland-окна параметры приходят нулевыми, и сторонний клиент не может получить корректную позицию.
   - Следовательно, **решение должно работать внутри композитора** (как расширение) или использовать привилегированный протокол (input-method).

2. **Как получают позицию каретки существующие решения?**
   - **GNOME:** Расширение `gnome-shell-extension-kimpanel` читает координаты окна, потому что работает внутри композитора. Расширение `Better IBus` показывает подсказку источника ввода при фокусе на текстовых полях, хотя отмечает возможные неточности из-за задержек обновления позиции. Это подтверждает принципиальную возможность.
   - **AT-SPI (Accessibility):** Для некоторых приложений (GTK, Qt) позиция каретки может быть получена через AT-SPI (события `object:text-caret-moved`, `atspi_text_get_character_extents`). Это дополнительный источник данных, но не универсальный для всех приложений.

3. **Архитектурные варианты:**
   - **GNOME:** GNOME Shell Extension (JavaScript). Расширение подписывается на события смены источника ввода (IBus) и получает позицию каретки либо из внутренних API Shell (если доступно для focused window), либо через AT-SPI для активного приложения.
   - **wlroots (Sway и др.):** Потребуется модуль для композитора (например, на C/Rust, встраиваемый в wlroots) либо протокол `input-method-v2` (если композитор предоставляет доступ к `set_cursor_rectangle`). Универсального решения для всех wlroots-композиторов без их модификации нет; это документируется как ограничение и **не реализуется** в рамках проекта.
   - **Кроссплатформенная шина (опционально):** Для обмена состоянием раскладки между расширением и возможным демоном можно использовать D-Bus (например, публиковать текущую раскладку и координаты каретки в шину).

## 3. Рекомендуемая архитектура и стек

**Основной подход: расширение GNOME Shell + опциональный D-Bus-координатор.**

| Компонент | Технология | Ответственность |
| :--- | :--- | :--- |
| **GNOME Shell Extension** | JavaScript (GJS) | Отслеживание смены раскладки через IBus/`org.gnome.Shell`; получение позиции каретки (через AT-SPI или внутренние API Shell); отрисовка оверлея (Clutter actor) в нужной точке. |
| **D-Bus-сервис (опционально)** | Rust / Go | Централизованное отслеживание XKB-состояния (через `libxkbcommon` или `xkbcli`) и публикация текущей группы; расширение подписывается на сигналы. Упрощает синхронизацию, но не обязателен. |

**Почему не Rust/Go для GUI:** клиентское Wayland-приложение не имеет доступа к позиции каретки другого приложения, поэтому GUI-слой должен быть частью композитора.

## 4. План реализации

1. **Фаза 1: Исследование и прототип для GNOME**
   - Изучить API GNOME Shell для доступа к позиции каретки focused window (проверить `global.get_focus_window()`, AT-SPI, а также существующие расширения `kimpanel` и `Better IBus`).
   - Создать минимальное GNOME Shell Extension, которое при смене раскладки показывает Clutter-актор (текст «RU»/«EN») в позиции, полученной из AT-SPI (для GTK-приложений) или из внутренних данных Shell.
   - Зафиксировать ограничения: для каких приложений (GTK, Qt, Electron) позиция доступна, а для каких — нет.

2. **Фаза 2: Унификация и документация**
   - Если используется D-Bus-координатор, реализовать его на Rust (крейт `zbus`) для публикации состояния XKB.
   - Написать README с чётким разделением: «Поддерживается: GNOME (через расширение). Для Sway/wlroots требуется модуль композитора (не включён)».
   - Задокументировать, что позиционирование у каретки зависит от поддержки `text-input` или AT-SPI в целевом приложении; для приложений без такой поддержки индикатор может не отображаться или отображаться с погрешностью (но **не** у мыши).

3. **Фаза 3: Полировка**
   - Добавить настройки (длительность показа, шрифт, цвета).
   - Обеспечить, чтобы оверлей не перехватывал фокус ввода.
   - Протестировать в GNOME Wayland.

---

## 5. Критерии приёмки

- В GNOME Wayland при переключении раскладки в текстовом поле (например, в gedit или Firefox) индикатор появляется **рядом с кареткой**, а не у курсора мыши.
- При запуске утилиты текущая раскладка отображается у каретки (если фокус находится в текстовом поле).
- В README явно указано, что позиционирование у курсора мыши **не используется**; для окружений, где получение позиции каретки невозможно, указано ограничение.
- Код собирается и работает в GNOME.
